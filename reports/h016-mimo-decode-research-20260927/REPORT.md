## CPU dispatch, placement and synchronization

1. **Two materially different MXFP4 CPU paths exist.** Ordinary `MUL_MAT_ID` quantizes F32 activations to Q8_0, then calls `ggml_vec_dot_mxfp4_q8_0` for output rows. Its x86 implementation has AVX2/AVX branches and scalar fallback/remainder. Native weights are unpacked/scaled during arithmetic; this is not BF16 activation computation. [CPU type/dispatch L287–292,1477–1729](https://github.com/ggml-org/llama.cpp/blob/7ac59a6e3ad851cd41af00f678effab0598ba9a8/ggml/src/ggml-cpu/ggml-cpu.c#L287), [x86 dot L918–1002](https://github.com/ggml-org/llama.cpp/blob/7ac59a6e3ad851cd41af00f678effab0598ba9a8/ggml/src/ggml-cpu/arch/x86/quants.c#L918).
2. **`--no-host` allows repacking; it does not force a plain CPU buffer.** It skips CUDA host buffers before CPU extra buffers. CPU expert overrides explicitly consider extras. With repack enabled (source default), AVX2 MXFP4 tensors whose output rows divide by eight can use `CPU_REPACK` and eight-row Q8_0 GEMV; Pro's 2048/6144 rows qualify. The actual expert buffer remains unproven. [Buffer order L1090–1129](https://github.com/ggml-org/llama.cpp/blob/7ac59a6e3ad851cd41af00f678effab0598ba9a8/src/llama-model.cpp#L1090), [override L1235–1256](https://github.com/ggml-org/llama.cpp/blob/7ac59a6e3ad851cd41af00f678effab0598ba9a8/src/llama-model-loader.cpp#L1235), [repack eligibility L5094–5103](https://github.com/ggml-org/llama.cpp/blob/7ac59a6e3ad851cd41af00f678effab0598ba9a8/ggml/src/ggml-cpu/repack.cpp#L5094).
3. **Concrete limitation:** repacked expert `MUL_MAT_ID` groups by expert, statically splits output rows among threads and calls GEMV separately for each routed token row, including prefill. Its ordinary `MUL_MAT` GEMM switch is a different path. The alternative tiled CPU path excludes MXFP4 altogether. Thus increasing prefill batch does not automatically obtain an MXFP4 expert GEMM kernel. Route/weight reuse and GPU work can still help prefill. [Repack L4783–4913](https://github.com/ggml-org/llama.cpp/blob/7ac59a6e3ad851cd41af00f678effab0598ba9a8/ggml/src/ggml-cpu/repack.cpp#L4783), [tiled type gate L615–632](https://github.com/ggml-org/llama.cpp/blob/7ac59a6e3ad851cd41af00f678effab0598ba9a8/ggml/src/ggml-cpu/tiled/tiled.cpp#L615). A high-ISA library name does not establish a particular kernel or utilization of every ISA feature.
4. **Correction to blanket CPU-expert prefill claims:** `--cpu-moe` is a weight-placement override. Ordinary host weights can have operations offloaded by the scheduler; CUDA's default threshold is 32 token rows. Single-token decode does not meet that default. `CPU_REPACK` is not a host buffer for that scheduler condition, and stays on its CPU path. Actual prefill GPU offload is **not established**. [Scheduler L967–979](https://github.com/ggml-org/llama.cpp/blob/7ac59a6e3ad851cd41af00f678effab0598ba9a8/ggml/src/ggml-backend.cpp#L967), [CUDA L5615–5634,5804](https://github.com/ggml-org/llama.cpp/blob/7ac59a6e3ad851cd41af00f678effab0598ba9a8/ggml/src/ggml-cuda/ggml-cuda.cu#L5615). The expert-cache discussion's PCIe-every-token claim cannot be transferred to R5.
5. **NUMA/interleave are separate controls.** Load mode none disables mmap; interleave spreads new memory allocations round-robin, with allocation fallback, rather than pinning computation. GGML distribute sets a whole-node thread mask at graph execution, superseding initial strict per-thread affinity within the outer cpuset. Ordinary expert dynamic chunking is disabled with GGML NUMA; repack uses static row partitions. Poll 0 disables new-work polling, not graph barriers (non-OpenMP barrier spins; OpenMP uses its own barrier). GPU attention/CPU experts also require dependency-ordered graph splits and activation/routing/result copies. These costs recur layer by layer; no measured allocation of time among them is available. [Affinity/barriers L576–611,2171–2213,3105–3161](https://github.com/ggml-org/llama.cpp/blob/7ac59a6e3ad851cd41af00f678effab0598ba9a8/ggml/src/ggml-cpu/ggml-cpu.c#L2171), [split synchronization L1661–1705](https://github.com/ggml-org/llama.cpp/blob/7ac59a6e3ad851cd41af00f678effab0598ba9a8/ggml/src/ggml-backend.cpp#L1661).

The build recipe intentionally sets `GGML_NATIVE=OFF`, `GGML_BACKEND_DL=ON`, `GGML_CPU_ALL_VARIANTS=ON`; that is not a generic-only build. R creates named variants (`x64`, `haswell`, `skylakex`, `icelake`, `zen4`, etc.), scores CPUID-supported features and loads the highest-scoring accessible library. Search locations include compiled backend directory, executable directory and working directory. The recipe copies libraries into `/opt/llama` beside the executable. Successful loading is logged at INFO; per-candidate scores are compiled out with NDEBUG, so Release logs need not show them. [Variant list L487–519](https://github.com/ggml-org/llama.cpp/blob/7ac59a6e3ad851cd41af00f678effab0598ba9a8/ggml/src/CMakeLists.txt#L487), [loader L480–583](https://github.com/ggml-org/llama.cpp/blob/7ac59a6e3ad851cd41af00f678effab0598ba9a8/ggml/src/ggml-backend-reg.cpp#L480).

## Timing and pacing check

No `--tps`, token-bucket or generation-rate limiter was found in inspected pinned common argument/parameter and server loop/queue/task sources, nor in local launch/proxy code. This is a bounded source negative, not proof about every external component. Idle sleep -1 disables idle unloading; request token/time budgets stop generation rather than pace it. The Windows subprocess 50-ms polling fallback does not apply to this Linux inference loop.

Native timing uses `ggml_time_us()` timestamps after sampling synchronizes the context. Generation time runs from the first generated token to the latest; **steps = `predicted_n - 1`**, because prompt logits supply the first token. Thus `predicted_per_token_ms = predicted_ms/(N-1)` and `predicted_per_second = 1000*(N-1)/predicted_ms`. Stats reset for a new slot task. [Stats L350–429](https://github.com/ggml-org/llama.cpp/blob/7ac59a6e3ad851cd41af00f678effab0598ba9a8/tools/server/server-common.h#L350), [JSON L84–97](https://github.com/ggml-org/llama.cpp/blob/7ac59a6e3ad851cd41af00f678effab0598ba9a8/tools/server/server-common.cpp#L84), [sampling/timestamps L3863–3874](https://github.com/ggml-org/llama.cpp/blob/7ac59a6e3ad851cd41af00f678effab0598ba9a8/tools/server/server-context.cpp#L3863).

The 55-output 16K case therefore has 54 timed steps. Local MiMo proxy forwards original chunks using `read1/write/flush`; it does not normalize native timings. Historical benchmark code preserves raw N/ms, while some helpers derive N/ms; `glmrepair.py` explicitly emits both N/ms and (N-1)/ms. Client arrivals can coalesce and are a separate clock. The exact current W1 benchmark file is not established here. Reported 16K 1095.180648 vs 64K 1095.181341 ms/token differs by only 0.000693 ms, but source contains no matching fixed pacing constant. Compare raw final N/ms/derived fields, request identities and first/last native/SSE timestamps; W1 owns that check. Near-equality alone proves neither a limiter nor a fixed-cost kernel.

## Expert-byte planning arithmetic

Official pinned Pro config has 70 trunk layers, one dense plus 69 routed, hidden 6144, expert FFN 2048, 384 experts/top-8, no shared experts. Three expert matrices per layer are loaded by `mimo2.cpp:66–71`. An MXFP4 block stores 32 weights as 16 packed bytes plus one scale byte (`ggml-common.h:214–219`).

`69 × 8 × 3 × 6144 × 2048 × 17/32 = 11,069,816,832 B = 10.3095703125 GiB/token`.

All 384 experts occupy 494.859375 GiB; multiplying by 8/384 gives the same selected payload. This counts ~20.84B selected expert weights, not all 42B active parameters. BF16 GPU attention/nonexperts are excluded. It is a minimal one-pass logical expert payload under those assumptions, **not an unconditional lower bound on DRAM reads**: cache/route reuse can reduce memory-controller traffic; repeated reads, activation conversion, scratch and other consumers can increase it. At 0.913 tok/s it corresponds to ~10.107 decimal GB/s of logical payload, not measured RAM bandwidth. Unpacking, latency, inter-node traffic and barriers prevent converting a theoretical channel ceiling into guaranteed tok/s. No numeric channel ceiling is asserted without observed memory rate.

## CUDA and closest primary comparisons

R supports `120a-real`; CUDA >=12.8 adds SM120a and plain 12X targets are rewritten to 12Xa for architecture-specific FP4 instructions. The retained build recipe uses CUDA13.2.1/120a-real. MXFP4 MMQ supports expert IDs and defaults eligible Blackwell FP4 operations to Q4 activations (otherwise Q8_1; `GGML_CUDA_MMQ_PREC` can override). This is a **GPU-expert** path, not the CPU Q8_0 path. BF16 nonexpert storage does not imply BF16 activations everywhere. F16 Flash Attention explicitly handles K192/V128, mask/no-bias GQA optimization and ratio divisible by eight; Pro ratio16 qualifies dimensionally. Actual kernel/graph proof still matters. GPU 0–4% alone proves no CUDA defect.
