# H031 SOURCE03 — image dead-parent reconciliation proposal

Source/local-evidence review only, 2026-09-29. No image VM read, write, cleanup, start, stop, deployment, or recovery was performed for this proposal. This is an implementable proposal requiring ROOT review before implementation/activation; it is not an existing command or live acceptance result.

## Finding

The supported owner cannot presently settle these retained records after their parent exits. `Runtime.operation()` refuses any previous operation other than `complete`/`failed` before recovery admission. `recover()` also refuses an active operation or active recovery. `recovery_admission()` requires the active recovery's exact live PID/start-ticks unless the calling runtime is that recorded parent. `tests/image_runtime/test_operation_protocol.py::test_active_or_unresolved_operation_cannot_be_replayed_after_owner_exit` and `test_recovery_admission.py::test_dead_parent_identity_cannot_authorize_child` deliberately enforce this behavior. Do not weaken those rules globally.

A plain retry of the fixed recovery helper therefore cannot repair this incident. Clearing a flock file or changing `active` to `complete` would discard unresolved ownership, and a `warm=true` state is not API readiness. The retained `cleanup.backend_stopped=true` is not current physical proof: the exact retained native was running.

## Smallest explicit extension

Prefer one task-specific, root-only reconciliation helper, reviewed and hash-pinned as an activation artifact. Do not add it to the API sudo allowlist or give it arbitrary action/path/container arguments. It should load the exact still-installed old `service.py` only after matching the service hash above, and use that owner's current `Runtime`, anchored storage, `singleton`, `critical`, `exact_native`, `native_generation`, `reset_owned`, and `settle_native` primitives. Cleanup publishes JSON-loaded state and creates no new residency tuples, so the old owner primitives can perform cleanup without first changing their source/config pin. Deploy the serialization correction only after exact cleanup has settled. This avoids inventing a source-successor admission for active image records.

Use one protected, fixed-path reviewed plan binding all hashes and identities above, the helper's own SHA256, and the archive/consumption names. The plan authorizes only this abandoned start/recovery pair and exact native generation. Unknown/missing/changed fields, nonmatching source closure, or a previously consumed plan are refusals. It is a new explicitly reviewed settlement action, not continuation or successful completion of the dead owner's request.

1. Obtain anchored `recovery.lock`, then `operation.lock` nonblocking; never unlink/recreate locks. Follow the existing short common-lease ordering. Prove fresh storage/source/boot/hardware and exact identity before writes; read slow process/systemd/native evidence outside the common lease while holding both image locks, then revalidate at publication. Do not hold the common lease through native stop/remove.
2. Require the exact backend InvocationID; MainPID and ControlPID zero; no unit job or queued start/restart; no backend unit owner/cgroup process. Require both recorded owner PIDs absent from `/proc` (conservative refusal if either PID was reused, unreadable, zombie, or otherwise not provably absent). Recovery's old start ticks remain archived. A regex process scan alone is insufficient. Prove no live recovery/helper/telemetry/request child and no API busy request or pending recovery; API admission must remain closed. Verify descriptor ownership/no-replacement throughout. These checks must not stop or mutate the API or another model.
3. Read raw state/operation/recovery/config bytes through anchored protected paths; compare every raw hash, parsed full records, cross-links, boot, GPU, source closure and native tuple. Use `exact_native`/`validate_image_container` plus current PID/start ticks, StartedAt, labels, owner/run ID, image, name, policy/network and non-OOM identity. Validate only the selected exact image target and common hardware policy. Any unproved or changed native generation requires a new reviewed case, not automatic adoption.
4. Before replacing any record or stopping/removing the native, durably archive the exact original raw bytes plus config/source pins, complete native inspect, bounded exact-container logs (explicit since/until, byte/line cap and truncation receipt), relevant native-generation evidence, unit/process/lock/hardware proof, and both original failure receipts/journal identities in a private archive under the registered protected runtime root. Archive and hash the available invocation-specific receipts, native output/telemetry references and failure history; retain raw captures outside Git. Docker removal loses container-local inspection/log history, so an incomplete or failed evidence archive must block stop/remove. Preserve native identity and recoverable history, not a requirement to keep its running process alive after separately authorized exact cleanup. Use exclusive no-overwrite archive/consumption creation, anchored checks and fsync; verify archival digests. Preserve old archived bytes unchanged. Write a one-time consumed intent before any record mutation/native dispatch, binding archive and reviewed plan hashes. A crash after consumption leaves the case blocked for review; the helper must not automatically replay.
5. While holding both locks and a short common lease, mark the old operation `failed` with an explicit abandoned-owner reconciliation reason and archive reference, never `complete`. Replace the old recovery with a distinct new cleanup-only parent reservation (new token, current PID/start ticks, exact boot/config/GPU, archive/plan reference, retained child/prior invocation), status active/phase settle. Store the old records verbatim in the archive. Keep the old native/state intact at this handoff. The old `Runtime.recovery_record` equality branch can authorize this new parent's `reset_owned()` without pretending the dead parent is live. A crash between record writes still leaves at least one active unresolved record; never roll back records to reopen admission.
6. Release only the outer operation lock; retain recovery lock and the exact new active reservation. Do not expose an intermediate state with both operation and recovery inactive: the active cleanup reservation prevents normal start/recover, while the held recovery lock excludes any background API recovery helper. No API/config mutation or recovery request is authorized here. Call the ordinary `reset_owned()` once. It reacquires operation ownership, publishes stopping/warm false and invokes `settle_native(remove=True)`. Existing exact dispatch markers allow the first stop and remove here because neither existed in the reviewed predecessor. Never repeat create/start/warm, never clear or reuse an uncertain stop/remove marker. Do not issue another systemd stop/restart during this settlement: the exact unit is already settled and verified before admission. Preserve the uncertain historical warm marker in `last_native_actions` when physical removal permits rollover.
7. Require exact native stopped/PID0 before removal, then successful complete Docker inventory excluding exact ID and fixed name using `prove_absent`; prove exact generation's processes/cgroup/compute and listener are gone, retaining peer workloads. Produce an immutable failed-attempt/physical-settlement receipt. If this helper exits before the coordinated successor takes ownership, keep the cleanup recovery `active` with an explicit `settled_awaiting_reviewed_activation` phase and archive/settlement references. Even after its flock is released, the protected active record makes normal `recover()` refuse, so the background API cannot start image work in the handoff gap. Do not mark recovery `complete` merely to unblock a later command. Any exception preserves primary and settlement failures, archive/consumption and active ownership; no generic cleanup loop.

Multi-file writes are not an atomic transaction. The consumed intent plus write order must keep every crash point closed. Do not claim success based on archive creation, stale cleanup fields, or operation status alone.

## Subsequent ordinary sequence, separately reviewed

After exact cleanup reaches physically absent/stopped state, ROOT can review/install the narrow service serialization fix and exact updated config source hash, with unchanged runtime/image/model/network/hardware/profile values. The active cleanup reservation remains closed across deployment; no API changes are authorized by this proposal. Record both old and new pins and recheck full source closure.

There is currently no supported atomic transition from that closed reservation to ordinary `recover()`. The separately reviewed activation must therefore include a narrow handoff: under one continuously held recovery descriptor, verify the exact consumed plan/archive/settlement and allowed old-to-new source/config delta, close the old failed-settled reservation, and enter the ordinary corrected recovery body without releasing/reacquiring that descriptor. A small internal pre-held-descriptor entry can reuse the existing recovery body; it must not be exposed through API arguments, accept an arbitrary lock, or bypass ordinary native/hardware checks. Completing the old record, releasing the lock, then invoking the public helper is unsafe because a background API recovery could win that gap. If this handoff is not implemented/reviewed, retain the active reservation and report image blocked.

Only within separately authorized remaining time may that coordinated handoff run one ordinary reset/start/warm sequence and return its actual retained result. API readiness must be observed independently. No warm-result adoption, raw health shortcut, replay, benchmark, or automatic retry is proposed. No generation/admission is authorized by this proposal itself.

Before adding the helper, focused fixtures must show this exact abandoned pair settles once; live/PID-reused parent, busy/replaced locks, changed raw state/operation/recovery/config/source/boot/native/generation/unit/hardware or missing archived proof refuse before native mutation; old warm dispatch is never replayed; stop/remove timeouts remain unresolved and cannot repeat; crash points do not admit normal start/recover; source pins cannot change during cleanup; and all original failures/archives survive. Existing ordinary dead-parent rejection tests must continue to pass unchanged.
