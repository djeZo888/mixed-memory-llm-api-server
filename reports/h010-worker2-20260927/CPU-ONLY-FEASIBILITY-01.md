The helper fallbacks are real: CPU gate/decode math, convolution update, sparse MLA reference, embeddings, and generic AMX FP8 operations exist. They do not form a supported CPU end-to-end GLM service. In particular, disabling CUDA graphs, GPU expert staging or all resident GPU experts leaves the exact-model exclusion, KDA prefill, NSA CUDA capability setup and expert CUDA-stream bridge unresolved. The SM120 sparse MLA branch bypasses the FlashInfer TRTLLM ABI; it still runs its own CUDA/Triton implementation. This distinction prevents overstating a generic library dependency.

Our separate protective gate in `scripts/runtime/flash/owner.py:154-164` checks GPU identity, reserve and temperature and binds Docker to that GPU. It is not the reason the underlying model lacks CPU support, and was not weakened. Storage/authentication gates and all runtime configuration remain unchanged.

## Change assessment and limits

A CPU implementation would need complete KDA prefill and DSA/KPool integration, CPU scheduling in place of CUDA streams, compatible non-expert FP8 kernels, and preserved model/cache semantics. Dequantizing non-expert weights or changing quantization adds a precision/memory confound; changing engine/format is a migration. Existing CPU oracles are useful porting ingredients, not an activation proposal. No credible CPU RAM or speed estimate follows from this source-only check.

A short primary-source check of llama.cpp at `95887577ab5fead779581a7030a83c7752ff3234` found `glm4`/`glm4moe` in its [architecture registry](https://github.com/ggml-org/llama.cpp/blob/95887577ab5fead779581a7030a83c7752ff3234/src/llama-arch.cpp#L85-L86), not an established `glm5_next` path. This is a bounded registry/converter check, not a claim about every branch or future version. No exact-architecture CPU alternative was confirmed. GGUF conversion would change the existing engine/weight format and is outside this comparison. Alternative research stopped on root's finalization instruction.

**NOT_TESTED:** CPU model load/inference, CPU memory/performance, conversion, new runtime, larger occupied context, four-instance overlap, or a repeat native parent/child workflow. Target CPU ISA for generic FP8 non-expert kernels was not re-probed. Published revision provenance is established; only the key server-arguments module additionally matched the deployed-source hash pin. Worker1 retains live backend/binary ownership.
