# H010 — Flash 64K benchmark and concurrent service

Completed 27 September 2026 (Ljubljana time). **64K benchmark PASS; Sova
restored with all four model instances available.** CPU-only comparison was not
run because the pinned runtime lacks a supported CPU-only path.

The warmed GLM-5.3-Flash run passed a 65,536-token technical retrieval and
arithmetic fixture. Production remains at 480,000 configured tokens with its
full cache pool already allocated. No runtime, model, cache precision or GPU
placement changes were made.

An 8,192-token varied technical warm-up completed in 41.957 s, TTFT 32.654 s,
128 output tokens. Its output reached the warm-up cap; correctness is unproven
for that discarded timing sample.

The measured run had no host swap-in/out and no Flash cgroup swap. Peak sampled
Flash cgroup memory was 582.061 GiB, including file cache; minimum host available
RAM was 565.778 GiB. All 64 expert threads accumulated CPU time: about 16,226
CPU-seconds across a 261.835-second observation bracket, approximately 62 busy
guest-core equivalents. This does not prove physical host pinning or saturated
memory channels. A small host swap burst during warm-up is reported separately.

## Capacity interpretation

Configured capacity and occupied input are different. The pinned pool already
reserves about 3.246 GiB for attention cache at 480K, plus about 0.28 GiB of
fixed recurrent state. The model's declared 1,048,576-token limit would require
about 7.090 GiB for that cache component: an additional 3.844 GiB. That is a
memory candidate, not a demonstrated operating limit. With unchanged workspace,
that additional pool would leave about 53.64 GiB beyond the required 7% GPU
reserve, using the measured 64K minimum free memory. Long-context workspace,
runtime behavior, quality and speed remain untested beyond 64K occupied input.

Production stays at 480K. Do not fit total VRAM linearly to occupied context
sizes or extrapolate long-context throughput from the cache formula. The 650 GiB
Flash cgroup cap remains a separate host-side constraint; reclaimable file cache
must not be described as exclusive model RAM.

## CPU-only comparison

Not run: it is not a supported minor configuration change. The exact pinned
GLM architecture rejects CPU serving and depends on CUDA/Triton attention and
CUDA stream integration around its CPU experts. Zero GPU-resident experts does
not mean CPU-only inference. A comparison needs another qualified engine or a
substantial implementation effort; neither was undertaken here.

## Final service verification

The first overlap attempt completed both Qwen requests and one 1024×576 image
successfully, but the Flash test client missed its scheduled start and did not
submit. A proposed corrected launch was canceled before dispatch when both
workers could not arm in time. Four-way request overlap is therefore NOT_TESTED,
not a model failure. No further inference attempts were made.

Sova was restored normally, with final verification at **23:52:47 UTC on
26 September / 01:52:47 Ljubljana on 27 September**. App, health, status and
canonical availability checks passed. All four model instances were resident
and available; Flash retained its qualified 480000/65536 configuration.
The 26 sessions, 133 messages, 62 file records and 17,597 regular non-database
files retained their original content inventories. Search/status/admin services
were unchanged. No older database was restored or image quarantine manually
cleared. [Recovery receipt](../reports/h010-worker2-20260927/RECOVERY-02.json).

The first recovery recorder parsed the HTML status page as JSON after the app
