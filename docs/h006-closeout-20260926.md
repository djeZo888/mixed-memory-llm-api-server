# H006 — image recovery and system service topology

Date: 2026-09-26. Reviewed maintenance, node-record and status changes are deployed.

## Image incident and recovery

At 06:00 UTC, an unattended `libexpat1` security update invoked needrestart on
the image API, model-control API and node API. Image API startup ran its existing
recovery path: the old image backend stopped cleanly, but its replacement failed
before a new container was created. Thus the API process remained running while
the image model was unavailable. There was no demonstrated idle-scheduler crash
or GPU disappearance. The precise replacement-start refusal is **unknown**:
that invocation discarded its diagnostic output. Older native-failure fields
were stale and were not used as evidence for this incident.

The reviewed maintenance change defers needrestart's automatic selection of four
managed AI units to controlled maintenance. Security package installation remains
enabled. Deferred processes still need timely controlled restarts to use patched
libraries; explicit maintainer-script/manual restarts remain outside this rule.
Image start/recover/stop attempts now retain small sanitized, protected receipts
and journal records. Start admission waits briefly for the existing lifecycle
lock before mutation; it does not replay a dispatched operation. See
[maintenance implementation and procedure](h006-maintenance-robustness.md).

Exactly one canonical image restart was submitted. Its deterministic image
warm-up passed at 10:40:51 UTC. Native ownership, image API readiness/admission,
protected receipts and journal output passed. The two text Qwens retained their
container/image/process identities and 480,000-token contexts. No additional
image request, text inference, GPU reset, driver/ECC change or VM reboot occurred.

The initial node-operation receipt remained `running` after the model was warm.
Current completion probes passed in 0.14–0.17 seconds and no recovery helper
remained. Source review found that terminal-record lock failures could be
swallowed, leaving a stale running receipt. This is consistent with the evidence;
the exact historical exception is not recoverable. Its correction and conservative
record settlement are documented in the [machine-readable results](../reports/h006-service-topology-20260926/summary.json).

The correction preserves the selected action outcome and briefly waits for
terminal-record lock admission, without replaying any action. Only the node API
was stopped and started for activation. Existing startup reconciliation marked
the old uncertain operation `interrupted/operation_interrupted`, retaining its
original audit and request identity; it was not relabelled successful. An immediate
operation lookup initially returned 404 during startup; the refreshed authenticated
lookup returned 200 with the reconciled record. This startup observation remains
in the evidence. All three model identities and the existing image warm receipts
were preserved. See [terminal-record change](h006-terminal-metadata.md).

## Status and placement configuration

The deployed [registry](../ai-harness/config/system-registry.json) drives node
enumeration, passive observation transports and displayed service placement.
It includes both current VMs, seven managed services and 25 supporting or
in-process components. The status page puts both VM resource summaries first,
followed by a unified Service / Host / Type / State table and detailed resources.

- Existing native observations cover the seven services and the node-manager
  process. Four additional local probes report nginx, the administrative helper,
  the task egress watcher and the task-slice prerequisite with their own timestamps.
- Twenty other components are inventory-only: their independent state, readiness
  and observation age remain unknown. Parent availability is never substituted.
- Configured unreachable nodes remain listed. Missing metrics remain unknown.
- Additional compatible node-v1 producers can be monitored through separately
  credentialed, bounded private HTTP connections. A third-node mock verified this;
  no additional live VM was provisioned. Existing administration credentials are
  not automatically shared with new nodes.
- Only the existing supported lifecycle targets receive controls. Listing a new
  component or node does not authorize arbitrary commands or restarts.

The helper/status release changed only those two components. Main chat, search,
nginx, egress and task-slice process identities were preserved. Ledger row hashes,
chat/file/task counts and credentials were preserved. The exclusively locked
live owner.sqlite contents were not read; its metadata was unchanged.

**Portability boundary:** this is the configuration and observation foundation.
Registry edits do not move a workload or its data, change inference routing or
provision runtime/GPU/storage prerequisites. Existing inference endpoint consumers
remain in place. General workload relocation and semantic selection of new model
families require later implementation. See [configuration and extension guide](../ai-harness/docs/status-registry.md).

## Architecture and naming

`control` is custom deterministic model-lifecycle software, not an LLM. MiniMax
agents use Qwen for reasoning and delegation; the gateway schedules the two text
instances, and image tools invoke the separate image service. A future model
router may use an LLM to propose a specialist, while normal code enforces
availability, capabilities, budgets and permitted operations.

The [system diagram](system-topology-plan.md#current-logical-layout) shows these
roles and their hosting VMs. System name suggestions are **Sova**, **Sestav**,
**Nodus**, **Tandem** and **Polaris**. No name was selected and nothing was renamed.
Accounts and a reduced-information end-user view remain deferred as requested.
